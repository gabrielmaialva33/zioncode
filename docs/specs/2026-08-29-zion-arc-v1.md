# Zion ARC v1 Protocol Specification

Date: 2026-08-29

Status: **Draft interoperability candidate** — the Rust implementation and frozen Vector A exist and pass repository
tests; independent cryptographic review and external interoperability review remain pending

Protocol name: **Zion ARC — Adaptive Resilient Capsule**

## 1. Conformance language

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**,
**RECOMMENDED**, **NOT RECOMMENDED**, **MAY**, and **OPTIONAL** in this document are to be interpreted as described in
RFC 2119 and RFC 8174 when, and only when, they appear in all capitals.

An ARC v1 implementation is conforming only if it implements the byte layouts, validation order, algorithms, limits,
and carrier mapping in this document. Integer arithmetic used for lengths, offsets, dimensions, or allocations MUST be
checked arithmetic.

## 2. Goals, non-goals, and honest claims

ARC v1 transports one generic content item inside one lossless RGB PNG artwork. Its protocol pipeline is:

```text
content bytes
  -> whole-item zstd level 6
  -> encrypted envelope plus authenticated random padding
  -> XChaCha20-Poly1305
  -> systematic RS(255,K)
  -> column-major interleaving
  -> passphrase-keyed channel placement
  -> LSB matching in an RGB8 raster
```

ARC v1 is a new framing and transport protocol. It is not a new cipher. A conforming product MAY claim:

- offline confidentiality against an attacker who does not know a sufficiently strong passphrase;
- authenticated integrity of the public bootstrap, carrier dimensions, encrypted envelope, and recovered content from
  XChaCha20-Poly1305;
- the per-codeword Reed-Solomon correction budgets defined in Section 10;
- independent recovery of one capsule without another capsule;
- lossless round trips when the carrier dimensions and RGB channel values are preserved exactly;
- operation without a cloud service, account, analytics, or reader-side AI model.

An implementation MUST NOT claim that ARC is a novel cipher, unbreakable, post-quantum, formally verified, audited,
forensically invisible, plausibly deniable, or resistant to modern steganalysis. It MUST NOT claim survival through JPEG
conversion, resizing, screenshot capture, printing, camera capture, color correction, or social-media recompression.
ARC does not grant legal permission to bypass inspection or import rules.

The visible artwork is untrusted presentation data. ARC authenticates the 64 bootstrap bytes and dimensions as AEAD
associated data, and authenticates the envelope (including metadata, compressed content, and padding) as AEAD plaintext.
It does **not** authenticate PNG ancillary data, alpha, the upper seven bits of any RGB channel, unused channels, or the
appearance of the artwork. Changing any of those unauthenticated values can visibly alter an image without causing ARC
opening to fail. A product MUST NOT describe the complete artwork or PNG file as authenticated.

## 3. Threat model

The attacker is assumed to:

- know this specification and possess the complete encoder and decoder;
- view, copy, correlate, delete, reorder, and modify carrier files;
- read the public bootstrap, including collection and capsule identifiers, ciphertext size, and ECC profile;
- perform unlimited offline passphrase guesses, constrained only by the specified Argon2id cost;
- introduce bounded or unbounded corruption into carrier channels.

With a strong passphrase and uncompromised endpoints, ARC aims to keep envelope metadata and content confidential and to
reject unauthenticated plaintext. It does not hide the existence of an ARC capsule: the public `ZARC` magic is deliberate
and collection identifiers allow capsules in one collection to be correlated. CRC32C detects accidental bootstrap damage
but is not authentication. Authentication is provided only after successful XChaCha20-Poly1305 opening with the complete
bootstrap and carrier dimensions as associated data. The artwork surrounding those authenticated protocol values remains
untrusted as described in Section 2.

Recovery of bounded payload damage is in scope when width, height, bootstrap bytes, channel ordering, and keyed placement
remain unchanged. Specifically, for every 255-byte RS codeword, ARC guarantees recovery when the reconstructed codeword
contains no more unknown erroneous byte symbols than the selected profile permits in Section 10 (or satisfies the stated
error/erasure inequality when a conforming implementation supplies valid erasure locations).

The following are outside the threat model:

- a compromised encoder or reader, keylogger, unlocked device, memory inspection, or malicious OS;
- weak, reused, disclosed, or socially engineered passphrases;
- traffic analysis, file deletion, denial of service, and rollback to an older valid capsule;
- hiding ARC from forensic or statistical steganalysis;
- recovery after dimension changes, channel reordering, JPEG/resizing/color transforms, or other broad operations not
  reducible to the bounded reconstructed-symbol errors above;
- any corruption of the public bootstrap. Its CRC can detect accidents but the bootstrap has no ECC in v1;
- payload corruption beyond the selected profile's per-codeword correction inequality.

Reed-Solomon recovery is bounded per 255-byte codeword. Damage beyond a profile's bound can fail decoding or can be
miscorrected; the subsequent AEAD verification prevents miscorrected bytes from being returned as authenticated content.

## 5. PNG and RGB raster contract

The ARC wire carrier is a logical, row-major RGB8 raster stored in a lossless PNG. Canonical ARC writers MUST output an
8-bit truecolor PNG without alpha. A reader MAY accept another PNG color type only if its decoder produces exactly one
8-bit red, green, and blue value per pixel without a lossy color transform. Color profiles, ancillary chunks, PNG filter
selection, compression level, and other non-pixel metadata are not authenticated and are not part of the ARC protocol.

Lossless PNG re-encoding is supported only when width, height, and every RGB8 channel value remain identical. Byte-for-byte
PNG identity is not required. Alpha is never a carrier channel in ARC v1 and MUST NOT affect channel indexing.

For width `W`, height `H`, pixel `(x,y)`, and component `c` (`0=R`, `1=G`, `2=B`), the channel index is:

```text
channel_index = 3 * (y * W + x) + c
```

The flat channel array therefore has `C = 3 * W * H` bytes. Sealers and openers MUST reject:

- `W == 0`, `H == 0`, `W > MAX_DIMENSION`, or `H > MAX_DIMENSION`;
- `W * H > MAX_PIXELS`;
- a decoded RGB buffer whose length is not exactly `3 * W * H`;
- `C < BOOTSTRAP_CHANNELS + RS_N * 8`;
- a source PNG larger than `MAX_PNG_BYTES`.

### 5.1 Bounded PNG preflight and decode

PNG parsing is attacker-facing and MUST be bounded independently of the later ARC bootstrap checks. Before invoking a PNG
decoder, a conforming reader MUST:

1. wrap the input in a counting/capped reader that exposes at most `MAX_PNG_BYTES + 1` bytes; observing byte
   `MAX_PNG_BYTES + 1` is `InputTooLarge` and the decoder MUST NOT be invoked on that input;
2. read and retain the first 33 bytes without allocating from attacker-declared dimensions;
3. require the exact eight-byte PNG signature `89 50 4e 47 0d 0a 1a 0a`;
4. require the first chunk to have big-endian length 13 and type `IHDR`, then parse the IHDR width and height as
   big-endian `u32` values;
5. checked-compute `pixels = W * H`, `raster_bytes = pixels * 3`, and
   `permutation_indices = raster_bytes - BOOTSTRAP_CHANNELS`, and enforce all Section 4 and Section 5 limits before any
   raster-sized allocation; and
6. reject unsupported IHDR bit-depth/color-type combinations, compression method other than 0, filter method other than
   0, or interlace method other than 0 or 1.

The mandatory input format is bit depth 8, color type 2 (truecolor RGB). The optional color-type conversions mentioned
above are conforming only when the implementation can prove that its configured transform produces exactly RGB8 without a
lossy color conversion; acceptance of them is not required.

Before reading IDAT data, the implementation MUST configure its decoder's allocation/output limits. For `png` 0.18.1,
this means constructing the decoder with `png::Limits { bytes: MAX_PNG_DECODER_BYTES }` (or an equivalently strict
mechanism), selecting any allowed output transformation, reading header information, and rejecting unless the reported
post-transform output is RGB with eight bits per component and its reported output buffer size is exactly
`raster_bytes <= MAX_RASTER_BYTES`. A decoder API that cannot impose limits before IDAT inflation MUST NOT be used for an
ARC opener.

The caller then allocates exactly `raster_bytes`, decodes exactly one PNG image, requires the decoder to report exactly
`W`, `H`, RGB8 and `raster_bytes` written, and rejects APNG additional frames. After decoding, it MUST again require
`rgb.len() == 3 * W * H` using checked arithmetic. It MUST continue parsing through the first valid `IEND`, then drain the
capped reader to EOF and reject if even one byte follows `IEND`. This EOF drain remains subject to the
`MAX_PNG_BYTES + 1` counter, so oversized trailing input cannot evade the file-size limit. These checks all occur before
allocating the channel permutation.

## 6. Public bootstrap

### 6.1 Layout

The first 64 bytes discovered from a carrier form this fixed bootstrap. Semantic metadata such as item name, media type,
canonical order, corpus name, attribution, content length, and content hash MUST NOT appear here.

| Offset | Field | Width | Encoding, allowed value, and maximum | Rationale |
|---:|---|---:|---|---|
| 0 | `magic` | 4 | ASCII `ZARC` | Identifies ARC, distinctly from `ZION` and `ZSTG` |
| 4 | `version` | 1 | `0x01` only | Exact protocol dispatch; version zero is invalid |
| 5 | `bootstrap_len` | 1 | `64` only | Rejects layout confusion before field access |
| 6 | `ecc_profile` | 1 | `0=Safe`, `1=Balanced`, `2=Dense` | Selects `K` and the correction budget |
| 7 | `flags` | 1 | `0` only in v1 | Reserved; unknown semantics are rejected |
| 8 | `collection_id` | 16 | 128 random bits; all-zero forbidden | Argon2id salt identity and collection correlation |
| 24 | `capsule_id` | 16 | 128 random bits; all-zero forbidden | Unique sealing identity and nonce input |
| 40 | `ciphertext_len` | 4 | `u32`; `1..=1,011,712`; exact profile relation below | Bounds extraction and allocation |
| 44 | `codeword_count` | 2 | `u16`; `1..=4,096` | Bounds RS and interleave geometry |
| 46 | `suite_id` | 1 | `1` only | Freezes Argon2id, BLAKE3, XChaCha20-Poly1305, RS, and placement suite |
| 47 | `density_id` | 1 | `1` only, meaning exactly `33/100` | Freezes the v1 channel-use ceiling |
| 48 | `reserved` | 12 | all bytes zero | Canonical encoding and future version separation |
| 60 | `bootstrap_crc32c` | 4 | CRC-32C of bytes `[0,60)`, stored little-endian | Fast accidental-damage discovery; not authentication |

CRC-32C is the Castagnoli CRC with reflected polynomial `0x82F63B78`, initial value `0xFFFFFFFF`, and final XOR
`0xFFFFFFFF`. It covers bytes 0 through 59 exactly and excludes the stored CRC.

For the selected profile, parsers MUST derive `K` as specified in Section 10 and require:

```text
ciphertext_len == codeword_count * K
interleaved_len = codeword_count * 255
```

The parser MUST validate the CRC before performing Argon2id. CRC success does not make any field trustworthy; all 64
bootstrap bytes are later authenticated as AEAD associated data.

### 6.2 Bootstrap embedding and discovery

Bootstrap bytes are converted to bits most-significant bit first within each byte. Bit `i` is stored in the least
significant bit of channel `i`, for `0 <= i < 512`.

The bootstrap uses deterministic minimal LSB matching. Given channel byte `v` and target bit `b`:

```text
if (v & 1) == b: output v
else if v == 255: output 254
else: output v + 1
```

This changes a mismatching channel by exactly one and is intentionally public. Discovery reads `channel[i] & 1`, groups
each consecutive eight bits most-significant bit first, and parses the resulting 64 bytes.

## 7. Encrypted envelope

### 7.1 Fixed header and variable fields

The AEAD plaintext is one envelope. Its first 64 bytes have this layout:

| Offset | Field | Width | Encoding and validation |
|---:|---|---:|---|
| 0 | `magic` | 4 | ASCII `ARCE` |
| 4 | `version` | 1 | `0x01` only |
| 5 | `header_len` | 1 | `64` only |
| 6 | `compression_id` | 1 | `1`, meaning one zstd frame compressed at level 6 |
| 7 | `flags` | 1 | `0` only |
| 8 | `original_len` | 8 | `u64`, `0..=MAX_ORIGINAL_LEN` |
| 16 | `compressed_len` | 4 | `u32`, `1..=MAX_COMPRESSED_LEN`, and bounded by the remaining authenticated envelope |
| 20 | `name_len` | 2 | `u16`, `1..=MAX_NAME_LEN` |
| 22 | `media_type_len` | 2 | `u16`, `1..=MAX_MEDIA_TYPE_LEN` |
| 24 | `attribution_len` | 2 | `u16`, `0..=MAX_ATTRIBUTION_LEN` |
| 26 | `padding_len` | 2 | `u16`, `0..=246`, also `< K`, and equal to the formula in Section 9 |
| 28 | `content_hash` | 32 | Unkeyed BLAKE3-256 of the original content bytes |
| 60 | `reserved` | 4 | all bytes zero |

The variable bytes immediately follow the fixed header, with no alignment gaps:

```text
offset 64                                      name, name_len bytes
then                                           media_type, media_type_len bytes
then                                           attribution, attribution_len bytes
then                                           compressed_payload, compressed_len bytes
then                                           random_padding, padding_len bytes
end                                            exactly at AEAD plaintext length
```

`name`, `media_type`, and `attribution` MUST be well-formed UTF-8. `name` and `media_type` MUST NOT contain U+0000.
`attribution` MAY contain line feeds and MAY be empty for content that requires no attribution. Licensed content packers
MUST populate attribution as required by the content license. The ARC core performs no Unicode normalization and treats
the encoded UTF-8 bytes as authoritative.

All envelope semantics are encrypted. Before slicing any variable field, an opener MUST validate every declared length,
checked-add the complete expected size, and require that it equals the AEAD plaintext length exactly.

### 7.2 Content compression and verification

The original item is compressed as one zstd frame at compression level 6 before envelope construction. No dictionary,
raw fallback, per-block compression, skippable frame, concatenated frame, or trailing byte is permitted. ARC does not
normalize or reinterpret the original content.

Different conforming zstd encoders can produce different valid level-6 frames. This does not affect decoding
interoperability. Deterministic vectors pin the implementation versions in Section 17.

After authenticated opening, a decoder MUST decompress with a hard output limit of `original_len`, MUST require exactly
`original_len` output bytes, and MUST verify that unkeyed BLAKE3-256 of that output equals `content_hash`. It MUST return no
content before all three checks succeed.

The zstd decoder MUST be initialized without a dictionary and with a maximum window of
`MAX_ORIGINAL_LEN = 16,777,216` bytes before it consumes any frame bytes. With libzstd this requires both inspecting the
frame header and rejecting `windowSize > MAX_ORIGINAL_LEN`, and setting `ZSTD_d_windowLogMax = 24` (for `zstd` 0.13.3,
`Decoder::window_log_max(24)`) on the decompression context. A decoder that cannot enforce the window limit before frame
allocation is nonconforming. The input buffer is already bounded by `compressed_len <= MAX_COMPRESSED_LEN`; the
caller-owned output allocation MUST be exactly `original_len`.

The window/output limits are distinct from decoder overhead. Excluding the caller-owned compressed input and exact output
buffers, the zstd decoder's aggregate workspace MUST NOT exceed `MAX_ZSTD_DECODER_BYTES`. A conforming libzstd streaming
implementation MUST check `ZSTD_estimateDStreamSize(MAX_ORIGINAL_LEN)` before decoding and use either a bounded static
workspace or an allocation-accounting allocator that enforces this aggregate limit. For pinned libzstd 1.5.7 the estimate
is 17,266,488 bytes, within the 20 MiB budget. An implementation using stable caller-output mode MAY use less workspace,
but remains subject to the same maximum. Valid context, table, and streaming-buffer overhead is therefore permitted while
the frame window itself remains capped at 16 MiB.

Decompression MUST use a streaming single-frame API that exposes input consumption. Feed exactly the declared
`compressed_len`-byte slice, stop only when the decoder reports end-of-frame, and require all of the following:

- end-of-frame occurs exactly once;
- the input cursor equals `compressed_len` at that end (an early frame end is trailing input and is rejected);
- no skippable or concatenated second frame is accepted;
- the output cursor never exceeds `original_len` and equals `original_len` at frame end; and
- the frame header's content size, when present, equals `original_len`.

Convenience functions that automatically concatenate frames, allocate from an untrusted frame size, or do not reveal
whether the full input slice was consumed MUST NOT be used by an ARC opener.

## 8. Identifiers, Argon2id, and ARC domain separation

### 8.1 Identifier requirements

A collection creator MUST obtain a new 16-byte `collection_id` from the operating system cryptographic random-number
generator and MUST regenerate if it is all zero. Every seal operation MUST independently obtain a new 16-byte
`capsule_id` from the OS CSPRNG and MUST regenerate if it is all zero or already used with the same `collection_id`.

All capsules in a deliberate collection reuse its `collection_id` and may reuse an in-memory `collection_key`. A reseal
of identical content, metadata, or carrier MUST use a fresh `capsule_id`. Production APIs MUST NOT accept caller-selected
capsule IDs. Batch APIs MUST track generated capsule IDs for the batch and reject or regenerate collisions.

Reusing a `(collection_id, capsule_id)` pair with the same passphrase violates ARC v1 because it repeats the AEAD key and
nonce construction. Random 128-bit identifiers make accidental collision negligible but do not remove the implementation
requirement.

### 8.2 Collection key

Passphrases are opaque byte strings of length `1..=MAX_PASSPHRASE_LEN`. The protocol does not perform Unicode
normalization. A UI that accepts text MUST encode and reproduce the same UTF-8 bytes on every platform and SHOULD clearly
document its input policy.

First derive the 16-byte Argon2id salt:

```text
salt_full = BLAKE3-DERIVE-KEY(
    context = "zioncode ARC v1 Argon2id salt 2026-08-29",
    material = collection_id
)
argon2_salt = salt_full[0..16]
```

Then derive exactly 32 bytes with Argon2id version 0x13:

```text
collection_key = Argon2id(
    password = passphrase,
    salt = argon2_salt,
    secret = empty,
    associated_data = empty,
    memory = 65,536 KiB,
    iterations = 3,
    parallelism = 4,
    output_length = 32
)
```

The result is the raw 32-byte Argon2 tag. It is not a PHC string and no base64, textual prefix, terminator, or encoded
parameter block participates in later derivations. Argon2's optional secret and associated-data inputs are both the empty
byte string.

The collection key and passphrase MUST be kept out of logs and SHOULD be held in zeroizing memory. An implementation MAY
cache the collection key in memory to open or seal multiple capsules in the same collection; it MUST NOT persist the key
without a separate explicit secure-storage design.

### 8.3 Capsule values

`BLAKE3-DERIVE-KEY` means BLAKE3's standard `derive_key(context, material)` operation and returns 32 bytes. Context strings
below are exact, case-sensitive UTF-8 bytes without a terminating NUL.

Construct these fixed materials:

```text
key_material     = collection_key || collection_id || capsule_id
carrier_material = key_material || width_le_u32 || height_le_u32
nonce_material   = collection_id || capsule_id
```

Derive:

```text
aead_key = BLAKE3-DERIVE-KEY(
  "zioncode ARC v1 XChaCha20-Poly1305 key 2026-08-29", key_material)

nonce_full = BLAKE3-DERIVE-KEY(
  "zioncode ARC v1 XChaCha20-Poly1305 nonce 2026-08-29", nonce_material)
nonce = nonce_full[0..24]

permutation_seed = BLAKE3-DERIVE-KEY(
  "zioncode ARC v1 carrier permutation seed 2026-08-29", carrier_material)

matching_seed = BLAKE3-DERIVE-KEY(
  "zioncode ARC v1 LSB matching seed 2026-08-29", carrier_material)
```

Because `capsule_id` is unique within a collection, both the capsule-specific key and 24-byte nonce differ for every seal.
Implementations MUST test this construction by sealing the same item twice and asserting distinct capsule IDs, nonces,
keys, and ciphertexts.

## 9. Authenticated padding and XChaCha20-Poly1305

Let `base_len` be:

```text
base_len = 64 + name_len + media_type_len + attribution_len + compressed_len
```

For profile data width `K`, compute:

```text
padding_len = (K - ((base_len + AEAD_TAG_LEN) mod K)) mod K
```

Generate exactly `padding_len` bytes with the OS CSPRNG, store the length in the encrypted envelope header, and append the
bytes after the compressed payload. Padding is therefore inside the AEAD plaintext and authenticated. It has no semantic
meaning. The resulting ciphertext length, including the Poly1305 tag, is an integral multiple of `K`.

Serialize the complete 64-byte bootstrap, including its CRC, before encryption. Associated data is exactly 72 bytes:

```text
aad = bootstrap[0..64] || width_le_u32 || height_le_u32
```

Seal the padded envelope with the XChaCha20-Poly1305 construction implemented by RustCrypto `chacha20poly1305` 0.10.1
`XChaCha20Poly1305`, using the 32-byte `aead_key`, 24-byte `nonce`, and `aad`. The output is
`ciphertext || 16-byte_tag`, in the ordering produced by RustCrypto `Aead::encrypt` with
`Payload { msg: envelope, aad }`. This is the HChaCha20 extended-nonce construction; it MUST NOT be replaced with the
12-byte-nonce ChaCha20-Poly1305 variant.

No unauthenticated semantic metadata is permitted. A wrong passphrase derives the wrong keyed placement and will commonly
fail RS decoding before AEAD. Therefore, after successful KDF completion, the production open API MUST collapse every
placement, RS, AEAD, envelope, decompression, length, and hash failure into the single generic error `RecoveryFailed`.

## 10. Reed-Solomon and interleaving

ARC v1 uses systematic Reed-Solomon codewords over GF(256). The wire definition below is normative and does not depend on
a crate's undocumented behavior. It has been checked against Rust crate `reed-solomon` 0.2.1
`Encoder::new(255 - K).encode(data)`.

| Bootstrap code | Profile | Code | `K` | Parity | Unknown-byte correction budget per codeword |
|---:|---|---|---:|---:|---:|
| 0 | Safe | RS(255,223) | 223 | 32 | 16 |
| 1 | Balanced | RS(255,239) | 239 | 16 | 8 |
| 2 | Dense | RS(255,247) | 247 | 8 | 4 |

### 10.1 Finite field and polynomial representation

A field byte is the polynomial-basis representation in
`GF(2)[x] / (x^8 + x^4 + x^3 + x^2 + 1)`. The primitive polynomial including its `x^8` term is `0x11d`; after dropping
that term, the reduction byte is `0x1d`. Field addition and subtraction are bytewise XOR. The primitive element is
`alpha = 0x02`, with `alpha^0 = 0x01`.

The following algorithm completely defines field multiplication; all variables are unsigned bytes except the loop
counter:

```text
gf_mul(a, b):
    result = 0
    repeat exactly 8 times:
        if (b & 1) != 0: result = result XOR a
        high = a & 0x80
        a = (a << 1) & 0xff
        if high != 0: a = a XOR 0x1d
        b = b >> 1
    return result
```

Polynomial coefficient arrays are ordered from highest degree to constant term. Evaluation uses Horner's rule in that
same order. Let `P = 255 - K`. Construct the monic generator polynomial

```text
g_P(x) = product over i=0..P-1 of (x + alpha^i)
```

using field operations above. An implementable high-coefficient-first construction is:

```text
g = [0x01]
root = 0x01
repeat P times:
    next = [0x00; len(g) + 1]
    for j in 0..len(g):
        next[j]     = next[j]     XOR g[j]
        next[j + 1] = next[j + 1] XOR gf_mul(g[j], root)
    g = next
    root = gf_mul(root, 0x02)
```

As cross-checks, the complete generator coefficients for the three profiles are:

```text
P=8:
01 ff 0b 51 36 ef ad c8 18

P=16:
01 3b 0d 68 bd 44 d1 1e 08 a3 41 29 e5 62 32 24 3b

P=32:
01 74 40 34 ae 36 7e 10 c2 a2 21 21 9d b0 c5 e1 0c
3b 37 fd e4 94 2f b3 b9 18 8a fd 14 8e 37 ac 58
```

### 10.2 Systematic encoding and decoding geometry

For one exactly `K`-byte data chunk, byte 0 is the coefficient of `x^(K-1)` before parity space is appended. Encode it
as follows:

```text
work = data || [0x00; P]
for i in 0..K:
    coefficient = work[i]
    if coefficient != 0:
        for j in 1..P inclusive:
            work[i + j] = work[i + j] XOR gf_mul(g[j], coefficient)
parity = work[K..255]
codeword = data || parity
```

Thus a wire codeword is always exactly 255 bytes, its first `K` bytes are unchanged message bytes, and its final `P`
bytes are parity. When the complete codeword is viewed high-coefficient-first, byte 0 is the coefficient of `x^254` and
byte 254 is the constant term.

For opening, compute the `P` syndromes

```text
S_i = evaluate(codeword, alpha^i), for i = 0..P-1
```

with the field and coefficient order above. All-zero syndromes mean that the first `K` bytes may be passed to the next
stage. For every received codeword that differs from a valid codeword in at most `floor(P/2)` unknown byte positions, a
conforming decoder MUST successfully recover that valid codeword and return its original first `K` bytes; failing an
in-bound pattern is nonconforming. After correction it MUST recompute all `P` syndromes, require every one to be zero, and
only then return the first `K` bytes. Berlekamp-Massey/Chien/Forney, Euclidean decoding, or another algorithm MAY be used;
the correction guarantee, accepted codeword geometry, and final syndrome condition are identical.

An erasure API is OPTIONAL. If an implementation accepts erasure locations, it MUST successfully recover every valid
combination satisfying `2 * unknown_errors + erasures <= parity_bytes`, provided all supplied erasure locations are
correct and distinct. ARC v1's ordinary PNG opener has no erasure locations, so only the unknown-byte budget may normally
be claimed. The budget is per 255-byte codeword, not a global guarantee over the image. Outside the applicable inequality,
decoding may fail or miscorrect; subsequent AEAD verification prevents a miscorrected plaintext from being returned as
authenticated content.

Split the authenticated ciphertext into `codeword_count` consecutive `K`-byte chunks. Encode chunk `j` to codeword
`cw[j][0..255]`. Interleave column-major:

```text
interleaved[r * codeword_count + j] = cw[j][r]
for r in 0..255
for j in 0..codeword_count
```

Thus `interleaved.len() == codeword_count * 255`. Opening performs the exact inverse before RS decoding. RS decoding MUST
happen before AEAD opening. A decoder MUST discard all intermediate data if any RS codeword fails or if AEAD verification
fails; production reports either condition only as `RecoveryFailed`.

## 11. Capacity

The first 512 channels are reserved for the bootstrap. ARC v1 permits payload use of at most exactly 33 percent of the
remaining channels. For a valid `W x H` RGB8 raster:

```text
channels          = 3 * W * H
candidate_bits     = channels - 512
usable_bits        = floor(candidate_bits * 33 / 100)
carrier_codewords  = floor(usable_bits / (255 * 8))
max_codewords      = min(carrier_codewords, 4096)
```

A capsule fits only if `codeword_count <= max_codewords`. For profile `K`, the maximum AEAD plaintext length is
`max_codewords * K - 16`. The maximum compressed payload additionally subtracts the 64-byte envelope header and actual
UTF-8 metadata lengths. Padding consumes only the otherwise unusable tail needed to align the AEAD output to `K`.

### 11.1 Exact 1080x2340 calculation

For `W=1080`, `H=2340`:

```text
pixels             = 1080 * 2340             = 2,527,200
channels           = 2,527,200 * 3           = 7,581,600
candidate_bits     = 7,581,600 - 512          = 7,581,088
usable_bits        = floor(7,581,088 * 33/100)= 2,501,759
max_codewords      = floor(2,501,759 / 2,040) = 1,226
interleaved bytes  = 1,226 * 255              = 312,630
unused usable bits = 2,501,759 - 1,226*2,040  = 719
```

Profile capacities at this resolution are:

| Profile | AEAD ciphertext bytes | Maximum AEAD plaintext bytes | Maximum compressed bytes with empty attribution and minimum 1-byte name/media type |
|---|---:|---:|---:|
| Safe | `1,226*223 = 273,398` | 273,382 | 273,316 |
| Balanced | `1,226*239 = 293,014` | 292,998 | 292,932 |
| Dense | `1,226*247 = 302,822` | 302,806 | 302,740 |

The final column subtracts 64 envelope bytes, a one-byte name, and a one-byte media type. Real metadata reduces it by its
actual UTF-8 byte lengths. Safe is the default profile.

Only `codeword_count * 255 * 8` payload channels are modified or inspected after permutation. Smaller items therefore use
less than the 33-percent ceiling.

## 12. Keyed placement and payload LSB matching

### 12.1 ARC-PRNG

Placement and matching use the following self-contained deterministic generator, called `ARC-PRNG`. It is the 20-round
IETF ChaCha20 block function with a 256-bit key, a zero 96-bit nonce, and a 32-bit block counter starting at zero. ARC does
not use or depend on `rand_chacha::ChaCha20Rng` serialization, buffering, stream-number, or `next_u32` semantics.

For a 32-byte seed `s`, initialize sixteen 32-bit words:

```text
state[0..4]   = [0x61707865, 0x3320646e, 0x79622d32, 0x6b206574]
state[4+i]    = little_endian_u32(s[4*i .. 4*i+4]), for i=0..7
state[12]     = block_counter, initially 0
state[13..16] = [0, 0, 0]
```

Addition below is wrapping modulo `2^32`; `rotl` is 32-bit rotate-left. Define:

```text
quarter_round(a, b, c, d):
    a = a + b; d = rotl(d XOR a, 16)
    c = c + d; b = rotl(b XOR c, 12)
    a = a + b; d = rotl(d XOR a,  8)
    c = c + d; b = rotl(b XOR c,  7)
```

To produce one 64-byte block, copy `working = state`, perform exactly ten double rounds, then add the original state:

```text
repeat exactly 10 times:
    quarter_round(working[0], working[4], working[ 8], working[12])
    quarter_round(working[1], working[5], working[ 9], working[13])
    quarter_round(working[2], working[6], working[10], working[14])
    quarter_round(working[3], working[7], working[11], working[15])
    quarter_round(working[0], working[5], working[10], working[15])
    quarter_round(working[1], working[6], working[11], working[12])
    quarter_round(working[2], working[7], working[ 8], working[13])
    quarter_round(working[3], working[4], working[ 9], working[14])

output_word[i] = working[i] + state[i], for i=0..15
```

Serialize `output_word[0]` through `output_word[15]` as little-endian bytes, increment `state[12]` by one, and repeat.
Counter exhaustion MUST be rejected rather than wrapped. `next_u32()` returns consecutive `output_word` values in order
0 through 15 from each block; no bytes or words are skipped between blocks.

The fixed zero-seed check for `ARC-PRNG` is the following first 64 stream bytes (counter 0, zero nonce):

```text
76b8e0ada0f13d90405d6ae55386bd28
bdd219b8a08ded1aa836efcc8b770dc7
da41597c5157488d7724e03fb8d84a37
6a43b8f41518a11cc387b669b2ee6586
```

Equivalently, the first four `next_u32()` results are `0xade0b876`, `0x903df1a0`, `0xe56a5d40`, and
`0x28bd8653`.

### 12.2 Permutation

Checked-compute `candidate_count = channels - 512`, require
`candidate_count <= MAX_PERMUTATION_INDICES`, and allocate exactly `candidate_count` `u32` values. This allocation is at
most `MAX_PERMUTATION_BYTES = 50,329,600` bytes; implementations MUST NOT use pointer-sized integers for this normative
workspace. Fill it with every channel index in `[512, channels)`, in ascending order. Every channel index is representable
as `u32` under Section 4's limits.

Initialize an `ARC-PRNG` with `permutation_seed`. Apply in-place Fisher-Yates from the last element down to index one. For
each array position `i`, choose `j` uniformly in `0..=i` using:

```text
bound = i + 1
threshold = 2^32 mod bound
repeat:
    x = rng.next_u32()
until x >= threshold
j = x mod bound
swap(indices[i], indices[j])
```

All quantities in this loop are mathematical unsigned integers; implementations MUST avoid overflow when calculating
`2^32`; using `threshold = ((2^32 - bound) mod bound)` in at least 64-bit arithmetic is equivalent. The first
`interleaved.len() * 8` permuted indices are payload positions. An implementation MAY use a memory-saving algorithm only
if it produces byte-for-byte the same ordered positions and remains within the same explicit allocation bounds.

### 12.3 Matching

Convert interleaved bytes to bits most-significant bit first. Create an independent `ARC-PRNG` from `matching_seed`. For
every payload bit, consume exactly one `next_u32()` value `d`, even if the channel already has the requested LSB. Given
original channel `v` and target bit `b`:

```text
if (v & 1) == b: output v
else if v == 0: output 1
else if v == 255: output 254
else if (d & 1) == 0: output v - 1
else: output v + 1
```

Opening needs neither matching RNG nor original pixels. It reads `channel[position] & 1` in permutation order, groups
each eight consecutive bits most-significant bit first, and reconstructs the interleaved bytes.

## 13. Normative sealing algorithm

A conforming sealer MUST perform these steps in order:

1. Perform the capped PNG preflight and bounded exact decode in Section 5.1.
2. Validate profile, passphrase length, metadata UTF-8 lengths, `original_len`, and all fixed limits before compression.
3. Obtain or accept the collection's random `collection_id`; generate a fresh random `capsule_id` as in Section 8.1.
4. Compute `content_hash = BLAKE3(content)` and compress the complete content as one zstd level-6 frame.
5. Compute `base_len`, `padding_len`, projected ciphertext length, `codeword_count`, and carrier capacity. Reject before
   large allocation if any limit or exact relation cannot hold.
6. Fill the envelope header, append metadata, compressed payload, and OS-random padding in the exact Section 7 order.
7. Derive or reuse `collection_key`; derive `aead_key`, nonce, permutation seed, and matching seed.
8. Serialize the canonical bootstrap with `ciphertext_len = envelope.len() + 16`, compute CRC32C, and construct AAD.
9. XChaCha20-Poly1305 seal the envelope. Require the result length to equal the bootstrap `ciphertext_len` and to be an
   integral multiple of `K`.
10. Split ciphertext into `K`-byte chunks, RS encode each chunk, and column-major interleave the codewords.
11. Generate the keyed channel permutation and embed interleaved bits with the payload LSB rule.
12. Embed the public bootstrap in channels 0 through 511 with the bootstrap LSB rule.
13. Encode the resulting raster as a lossless RGB8 PNG. The sealer SHOULD immediately reopen the produced PNG and compare
    dimensions and all RGB channel values before reporting success.

The sealer MUST NOT overwrite the input cover on failure and MUST NOT log passphrases, keys, nonces, plaintext metadata,
or content.

## 14. Normative opening algorithm

A conforming opener MUST perform these steps in order:

1. Perform the capped PNG preflight and bounded exact decode in Section 5.1.
2. Read channels 0 through 511, reconstruct 64 bootstrap bytes, then validate magic, version, fixed length, CRC, profile,
   flags, suite, density ID, reserved bytes, and nonzero IDs.
3. Derive `K`; checked-multiply `codeword_count*K`, `codeword_count*255`, and the encoded bit count. Require all bootstrap
   length relations, global maxima, and carrier capacity before allocating ciphertext, codewords, or permutation memory.
4. Validate passphrase length, derive the collection key and capsule values, and reconstruct the exact 72-byte AAD.
5. Generate the keyed permutation; extract exactly `codeword_count*255*8` bits and reconstruct interleaved bytes. Every
   failure from this point through final success is exposed by the production API only as `RecoveryFailed`.
6. Deinterleave to exactly `codeword_count` 255-byte codewords. RS decode every codeword and concatenate their `K` data
   prefixes to reconstruct exactly `ciphertext_len` bytes.
7. XChaCha20-Poly1305 open with the derived key, nonce, and AAD; discard all intermediates on failure.
8. Require at least 64 plaintext bytes. Validate the complete fixed envelope header before reading variable data.
9. Checked-add every declared variable length, validate each maximum, require an exact total plaintext length, validate
   UTF-8, and require `padding_len` to equal the Section 9 formula.
10. Decode exactly one zstd frame with all Section 7.2 window, allocation, input-consumption, and output bounds; reject
    trailing input, decompression failure, output-length mismatch, or content-hash mismatch.
11. Only after every check succeeds, return content and encrypted metadata to the caller.

The opener MUST NOT return partial, unauthenticated, decompression-failed, length-mismatched, or hash-mismatched content.

## 15. Allocation limits and errors

Before any attacker-controlled allocation, a decoder MUST enforce the constants in Section 4 and the following derived
bounds:

```text
1 <= codeword_count <= 4096
ciphertext_len == codeword_count * K
interleaved_len == codeword_count * 255 <= 1,044,480
encoded_bits == interleaved_len * 8 <= usable_bits
AEAD plaintext length <= ciphertext_len - 16
all envelope component lengths checked-add to exact plaintext length
original_len <= 16,777,216
zstd decoder aggregate workspace <= 20,971,520
```

Before successful KDF completion, production APIs MAY expose typed errors equivalent to:

- `InputTooLarge`, `InvalidPng`, `UnsupportedPixelFormat`, `InvalidDimensions`, `CarrierTooSmall`;
- `BadMagic`, `UnsupportedVersion`, `InvalidBootstrapLength`, `BootstrapCrcMismatch`;
- `UnsupportedProfile`, `UnsupportedFlags`, `UnsupportedSuite`, `UnsupportedDensity`;
- `InvalidIdentifier`, `InvalidLength`, `CapacityExceeded`, `KdfFailed`.

After successful KDF completion the only production-facing error is `RecoveryFailed`. Test-only code MAY retain detailed
causes such as RS index, AEAD, envelope, zstd, length, or hash failure, but those diagnostics MUST NOT cross the production
facade, enter production logs/analytics/UI, or intentionally alter externally observable retry timing.

An API MUST NOT surface extracted or decrypted bytes on any error.

## 16. Versioning and compatibility

ARC v1 is a new protocol. It does not modify, extend, or reinterpret the frozen `ZION` codec v1 or `ZSTG` steganography
v1 formats. ARC uses public magic `ZARC` and encrypted-envelope magic `ARCE`; a `ZION` or `ZSTG` decoder MUST NOT be used
to open it.

An ARC v1 decoder accepts only `version == 1`, `bootstrap_len == 64`, `suite_id == 1`, `density_id == 1`, `flags == 0`,
and zero reserved bytes. It MUST reject version zero, unknown versions, larger or smaller bootstrap lengths, unknown
profiles, and unknown nonzero fields. A future change to layout, cryptographic ordering, KDF parameters, density, or field
semantics requires a new ARC version; silent fallback or downgrade is forbidden.

## 17. Determinism and test-vector contract

### 17.1 Production policy

Production sealing is intentionally nondeterministic. Collection creation, every capsule ID, and padding bytes MUST use the
OS CSPRNG. Resealing identical inputs MUST produce a different capsule ID, nonce, capsule key, ciphertext, placement, and
normally a different output raster. The decoder is deterministic for fixed PNG bytes and passphrase bytes.

Randomness injection is permitted only in a test-only or vector-generator API. Such an API MUST require explicit
`collection_id`, `capsule_id`, and exact padding bytes and MUST NOT be exposed by the production facade.

## 18. Security summary

ARC v1 deliberately composes established primitives in this order:

```text
whole-item zstd
  -> explicit authenticated padding
  -> XChaCha20-Poly1305 with bootstrap and dimensions as AAD
  -> RS(255,K)
  -> column-major interleave
  -> keyed permutation
  -> LSB matching
```

The passphrase and derived key are the secrets; the algorithm is not. CRC discovers bootstrap accidents, Reed-Solomon
repairs bounded ciphertext damage, and AEAD is the final authority for authenticity. Exact preservation of dimensions,
bootstrap, channel ordering, and all RGB8 values is the baseline lossless transport guarantee. Additionally, when
dimensions, bootstrap, and channel ordering remain unchanged, bounded changes to payload channels that stay within
Section 10's per-codeword inequality are guaranteed recoverable. Dimension changes, broad transforms, bootstrap damage,
and damage beyond that inequality have no recovery guarantee. Authentication covers
only bootstrap bytes, dimensions, the encrypted envelope, and recovered content; the visible artwork, upper channel bits,
unused channels, alpha, and PNG metadata remain untrusted.
